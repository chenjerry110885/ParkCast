# Running the collector

The collector is the only always-on component. Every day it is not running is a
training day that cannot be recovered, so the operational rules below matter
more than they would for a stateless service.

```bash
docker compose -f docker/docker-compose.yml up -d --build --force-recreate
docker compose -f docker/docker-compose.yml logs -f collector
```

## Hardened by default (2026-09-14)

`docker/docker-compose.yml` runs the collector non-root, read-only and capability-dropped
(`docs/superpowers/specs/2026-09-14-deployment-design.md` §5.4):

- **`read_only: true`**, with a small `tmpfs: /tmp:size=64m` for whatever needs to write there in
  passing. The only other writable places are the bind-mounted `../data` (the corpus) and
  `../../parkcast-scratch:/scratch` (snapshots — see "Analysing the corpus while it runs" below).
- **`cap_drop: [ALL]`** and **`security_opt: [no-new-privileges:true]`**; the image already runs as a
  fixed, unprivileged `uid 10001` (`docker/Dockerfile`), never root.
- **`cpus: "1.0"`** throttles CPU rather than killing the process, and **`pids_limit: 256`** — four
  times the measured peak of 6 processes (pyarrow's thread pools included), never set below the 256
  floor even though the measurement alone would allow lower.
- **Deliberately no memory limit.** An OOM kill of the one irreplaceable collector process would cost
  ticks that can never be re-fetched; Docker Desktop's own VM already bounds memory, so a second, harder
  limit only adds a way to lose data for no offsetting safety.

Rehearsed against a **snapshot copy**, never the live corpus, through a separate compose file with its
own project name so it can never be confused with the real stack:

```bash
docker compose -f docker/docker-compose.dryrun.yml run --rm rehearsal --day 2026-09-13
```

`docker-compose.dryrun.yml` (project `name: parkcast-dryrun`) binds `../../parkcast-dryrun/data` — a
copy, never `../data` — and has **no secret and no upload URL**, so it cannot touch the live corpus or
upload anything even called by mistake. Its entrypoint, `scripts/hardening-dryrun.py`, makes one
metadata request (what the collector does at startup and each day-rollover), proves the bind mount is
writable by uid 10001, that `pyproj` loads `proj.db` on a read-only root, and that a publish, a
compaction and a prune all complete, then prints `memory.peak` and `pids.peak` read straight from the
cgroup. Measured 2026-09-14: exit 0, `memory.peak=265166848` (≈253 MiB), `pids.peak=6` — comfortably
inside the settings above, so no fallback was needed.

**The secret, once it is wired in.** The live compose file will need a file secret
(`docker/secrets/parkcast_upload_secret`, git-ignored, generated by
`python scripts/new-upload-secret.py`) mounted at `/run/secrets/parkcast_upload_secret`, plus
`PARKCAST_UPLOAD_URL` reaching the collector — neither is in `docker/docker-compose.yml` yet.
Once it is, `docker compose up` will refuse to start the service if that secret file is missing, by
Compose's own file-secret behaviour. Until then the collector logs `uploads disabled (no valid upload
URL)` once at startup and behaves exactly as it does today. See [`../docs/deploy.md`](../docs/deploy.md)
for the full upload log line reference and the setup that creates the secret.

## `--force-recreate` is not optional

`docker compose up -d --build` rebuilds the image but **can leave the old
container running**. Compose recreates a container when it decides the service
changed; a rebuilt image with the same tag does not always count, so the
container keeps running the code it started with. The build output scrolls past
looking completely successful and the fix appears not to work — this cost real
confusion during Plan 2, where a change was debugged for several ticks before
anyone noticed the running container predated it.

Always deploy with:

```bash
docker compose -f docker/docker-compose.yml up -d --build --force-recreate
```

Confirm the new code is actually live before believing a result:

```bash
docker inspect -f '{{.State.StartedAt}}' docker-collector-1   # after the build
docker exec docker-collector-1 python -c \
  "import parkcast.forecast as f; print(f.__file__)"          # spot-check a change
```

## Never read `data/` from the host while the collector runs

The hot store is a WAL-mode SQLite file the collector is writing to. Read row
counts and run queries inside the container instead:

```bash
docker exec docker-collector-1 python -c \
  "import sqlite3; c=sqlite3.connect('/app/data/hot.sqlite'); \
   print(c.execute('SELECT COUNT(*) FROM observations').fetchone())"
```

For anything heavier, take a consistent snapshot with SQLite's backup API, writing it to
`/scratch` rather than to a file that is mid-write -- and rather than to `/tmp`, which is now a
64 MB `tmpfs` under the hardened settings above and would refuse a backup bigger than that:

```bash
docker exec docker-collector-1 python -c \
  "import sqlite3; s=sqlite3.connect('/app/data/hot.sqlite'); \
   d=sqlite3.connect('/scratch/snap.sqlite'); s.backup(d)"
```

`/scratch` is a bind mount straight to `D:/Projects/parkcast-scratch` on the host
(`docker-compose.yml`), so the snapshot is already at `D:/Projects/parkcast-scratch/snap.sqlite` --
no `docker cp` needed.

## Restarts are safe, and are verified

`PRAGMA synchronous=FULL` fsyncs every tick, so a stop loses nothing that was
already committed. Still, compare the row count before and after any restart:
an unexplained drop means the store, not the schedule, is the problem.

The collector logs one `tick data_ts=... rows=...` line and one
`published N lots x 24 horizons, M not updating` line per five-minute slot. Both
should appear within the first five minutes of a restart; if the publish line is
missing, the artifacts are stale even though collection is healthy. `M` counts
the lots published with no forecast because their feed has gone 24 hours without
an update (`src/parkcast/liveness.py`). A container still running an image built
before that rule logs the line without the `, M not updating` part — which is
also a quick way to tell whether a deploy actually took.

Once the upload secret is wired in (see above), every publish that follows also logs one upload line —
`uploaded: status=204 bytes=N duration=Ss` on success, or one of several other lines telling apart a
rejected, skipped or failed attempt. None of it can block or fail collection. Full reference:
[`../docs/deploy.md`](../docs/deploy.md) §6.

## A pause is not a stop

A pause is usually the user's own choice — gaming, a Windows update, freeing up RAM — not an incident to
go looking for a cause behind. What it costs is training data for that stretch, permanently; nothing
else breaks, and nothing here treats a stale or missing forecast as a fault (`docs/deploy.md`'s smoke
test and the app itself both treat it as a warning).

`restart: unless-stopped` covers a container that *exits*. A **paused**
container never exits: Docker freezes the process, the restart policy sees
nothing. On unpause the collector's overdue `sleep()` returns at once: it
polls immediately, off its usual phase (the tick after the 2026-09-13 pause
landed at 23:44:47), and is back in phase from the next slot. It logs nothing
about the gap itself — no error, no retry, no exhausted slot.

Measured 2026-09-13: a **Pause** click on the stack in Docker Desktop at
21:26:41 Taipei and a **Start** click at 23:44:46 cost 26 five-minute slots. The
collector's log went straight from the 21:26 tick to the 23:44 one. The host had
not slept — the Docker VM's `/proc/uptime` matched wall-clock time to within a
minute over 85 hours — and the container had not restarted.

The stack shows in the Docker Desktop dashboard as **`docker`**, because a
compose project takes the name of the directory its file lives in. That is
exactly the kind of name that gets paused while tidying up.

When coverage shows a gap, tell the causes apart before guessing:

```bash
docker inspect -f 'status={{.State.Status}} paused={{.State.Paused}} restarts={{.RestartCount}} started={{.State.StartedAt}}' docker-collector-1
```

- **Paused from the dashboard:** Docker Desktop's UI log records the click.
  Search `%LOCALAPPDATA%\Docker\log\host\electron-*.log` for
  `composePauseClicked` and `composeStartClicked`.
- **Host asleep:** the VM's uptime (`docker exec docker-collector-1 cat
  /proc/uptime`) should fall behind wall-clock time since Docker Desktop
  started by roughly the length of the gap, since a suspended VM does not
  count the time — this was used to rule a sleep *out* on 2026-09-13, not yet
  seen to rule one in — and the Windows System log carries Kernel-Power sleep
  and wake events.
- **Crash or stall:** the restart count rises, or the log shows
  `slot exhausted without a fresh tick`.

## Analysing the corpus while it runs

Anything heavier than a row count — `scripts/corpus-coverage.py`,
`scripts/evaluate-forecast.py`, an ad-hoc query — runs against a **snapshot**, in
a **throwaway container**, never against `data/` on the host:

```bash
# Written for Git Bash on the Windows desktop: MSYS_NO_PATHCONV=1 stops Git Bash
# rewriting container paths such as /scratch/snap into Windows paths.

# 1. A consistent copy taken by SQLite itself, plus the cold store, which is
#    only ever written by atomic rename. /scratch is a bind mount straight to
#    D:/Projects/parkcast-scratch on the host (docker-compose.yml), so this
#    writes the snapshot directly where the host can already read it -- no `docker cp`.
MSYS_NO_PATHCONV=1 docker exec -i docker-collector-1 python - <<'EOF'
import os, shutil, sqlite3
os.makedirs("/scratch/snap/data", exist_ok=True)
src = sqlite3.connect("/app/data/hot.sqlite")
dst = sqlite3.connect("/scratch/snap/data/hot.sqlite")
src.backup(dst)
dst.close(); src.close()
shutil.copytree("/app/data/cold", "/scratch/snap/data/cold", dirs_exist_ok=True)
EOF

# 2. Run the working tree's code on a writable copy inside a fresh container.
#    The scripts put ../src first on sys.path, so the image's installed copy is not used.
#    --user 0:0 because the image runs as uid 10001, which cannot create /work; every
#    mount here is read-only. Never add it to the live collector service.
MSYS_NO_PATHCONV=1 docker run --rm --user 0:0 \
  -v "D:/Projects/ParkCast/src:/repo/src:ro" -v "D:/Projects/ParkCast/scripts:/repo/scripts:ro" \
  -v "D:/Projects/parkcast-scratch/snap:/snapro:ro" docker-collector:latest \
  sh -c "mkdir -p /work && cp -r /snapro/data /work/data && cd /work && python /repo/scripts/evaluate-forecast.py"

# Clean up inside the container once you're done -- the bind mount means the host copy at
# D:/Projects/parkcast-scratch/snap survives this and can be deleted separately if you want it gone too.
MSYS_NO_PATHCONV=1 docker exec docker-collector-1 rm -rf /scratch/snap
```

The snapshot lands at `D:/Projects/parkcast-scratch/snap`, beside the repository and outside `data/` —
a live bind mount the host can already read, not a copy `docker cp` has to pull out of the container.
On Linux or macOS drop the `MSYS_NO_PATHCONV=1` prefixes and use the repository's own paths.

The Python test suite runs the same way on a machine whose Python has no pytest:
mount `src/`, `tests/` and `pyproject.toml` read-only into a throwaway
`docker-collector:latest` container, started as root with `--user 0:0` (the image's
own uid 10001 cannot install pytest), and run `python -m pytest` there:

```bash
MSYS_NO_PATHCONV=1 docker run --rm --user 0:0 -v "D:/Projects/ParkCast/src:/repo/src:ro" -v "D:/Projects/ParkCast/tests:/repo/tests:ro" -v "D:/Projects/ParkCast/pyproject.toml:/repo/pyproject.toml:ro" -w /repo -e PYTHONDONTWRITEBYTECODE=1 docker-collector:latest sh -c "pip install -q pytest 2>/dev/null; python -m pytest -q -p no:cacheprovider tests/"
```

`--user 0:0` is only ever for throwaway containers like these, never for the `collector` service.
